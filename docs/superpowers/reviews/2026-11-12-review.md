`1-the-first-release-v0-1-0`. The owner asked five things: where the bugs and inconsistencies are and how the

whether the interface is good; whether the prose is plain; and for one report and one plan. Each question has a
page of its own, and this page holds the answers in short, the decisions the plan waits on, and the plan.

## The answers

### Bugs

v0.1.0 can be published and cannot be installed. `bin/release pack` writes a `.sha256` file with no digest and
exits 0, so the loader and every consumer's workflow refuse the release (`bin/release:116`). The gate is red on
one test, and the stated minimum jq fails `kit check` on a correct file.

Past the release, the serious bugs are of four kinds.

- Trust and policy fail open. A clone that is not trusted gets its own bash run through what git answers for
  its top level, and a folder with a `kit.yml` and no `.git` is loaded unasked. `kit policy` runs opa, jq, and
  yq from directories the branch fills, so a branch can replace the tools that judge it.
- A verb changes the wrong thing. `kit work 7` adopts and pushes onto `release/7-0`. `kit commit` undoes two
  commits behind a stale index. Every hydrating verb rewrites `.kit/manifest` from the release, so a
  repository's own file under `.kit/` is replaced. The GitHub provider lets gh choose the repository and host.
- kittui acts in the wrong place. A form's verb runs where kittui started, not in the workspace shown. An
  action on another repository's issue runs on this repository's issue of the same number.
- kittui stops. Four sequences of keys or clicks crash it, a paste types nothing in any field, and a kit child
  that prompts on the terminal hangs behind the screen.

Of the 260 findings of 2026-11-10, 75 are fixed, 150 are open, 29 are partly fixed, and 6 were not rechecked.

### Inconsistencies

kit agrees with itself where one source drives a fact, and drifts where a fact is typed twice. The verb header
is the model: it feeds help, the form, completion, and the argument check for all 52 verbs. The drift is in the
spelling of an option's value (nine options take the next word, about thirty take only `=`), in three refusals
and two exit codes for one condition, in four shapes of list JSON, and in names: "change" against "pull
request", the Trust app whose verb is `kit audit`, and `kit workspace` one letter from `kit workspaces`.

The documents hold 922 of about 1,007 checked claims. The wrong ones sit where the code moved after the page,
and several are promises a newcomer acts on in the first hour: a Setup with no `kit trust`, a Homebrew line with
nothing behind it, and a welcome page that names Jira and Linear.

### Modularity, structure, and data

Neither side needs a new design. kittui's packages are layered with no cycle, and the bash has one loader, one
`use`, one verb preamble, and a forge contract with versions. What both sides lack is one home for each fact.

- 22 definitions live in both kit and kittui, and a test or a read at run time holds 4 of them. The structure
  page names one home for each of 14 facts typed in several places: the apps and their tabs, a tab's glyph and
  legend, the forge contract's 60 calls, what each forge is, and the hand-off to kittui, written ten times.
  `kit/modules/jq/glyphs.json` is the pattern to copy.
- The table has two hosts. Five screens stand on `table.Sheet`, and Flow implements the host itself in about
  1,050 lines, so every preset fix is owed twice. Six screens wire the menu bar and the search by hand.
- The tests are large, 1,261 bats tests and 1,022 Go tests, and each side of a seam is tested against a
  hand-kept copy of the other. 27 of kittui's 32 stage fixtures lack three keys that kit prints on every row.
- Time goes to starting processes. A text table forks about 23 shells a row, so `kit flow issues` at 300
  issues starts about 7,000 bash processes, against 254 with `--json`.

### Comprehensiveness

No. Of 174 promises in the README, `docs/features.md`, and the specs, 123 are built, 22 are built in part, and
29 are not built. The README and the features page are 87% built, 88 of 101. The seven specs are 52% built, 35
of 67. "Built" means the code is in the tree and no finding says it breaks the promise. None of it was run.

The holes cluster in five places: the release itself, GitLab and Azure DevOps beside GitHub, steps 4 to 7 of
the workspaces spec, the four decisions the entities spec gives the first release, and the bots spec. Two
things a user would expect are in no plan: a `CONTRIBUTING.md` with `CODEOWNERS`, and completion for bash and
fish. [Promised and not built](2026-11-12-review-gaps.md) has the table.

### Integrations

No, the research is not all in the product. It is 40 pages and 79 schema files. Outside git it holds 708
capability rows, and 156 have code: 59 of 91 for gh, 56 of 79 for glab, and 41 of 71 for az. AWS and the thirty
other tools, 425 rows over 34 services, have none.

Where a provider exists, the research and the code fit closely, but the code uses the research only as
reference. Nothing reads a schema except a gate loop that checks it against its own examples, and 20 of the
tests' 62 fixtures fail the schema of the command they fake. The integrations page gives a design in six steps
that makes the research drive code: the contract as one data file, one declaration per tool, tests drawn from
the schemas, generated page tables, a generic provider that runs a declaration, and an opt-in live run. It also
gives the order to build providers: depth in the three forges first, then the tracker seam with Jira and
Linear, Bitbucket Cloud, Gitea and Forgejo, a CD seam with Argo CD, and a CI seam.

### The interface

It is good, and a stranger will find it broken. The command line is good now: a refusal is one line that says
what is wrong and names the command that fixes it. kittui's table is the strongest part of the product, with
grouping, filters, saved presets, and a keys bar computed from where the keyboard is.

The frame around the table fails a newcomer in the first ten minutes. ⏎ on a row does nothing. Nothing on the
screen says how to quit. A paste types nothing. One unshifted key assigns every selected issue. `kit commit
--help` opens a page that never loads. On a light theme the cursor's row cannot be read. A dead key says
nothing, so a newcomer takes each of these for a defect. The faults are small, and none changes the design.

The interface page has the two tables the owner asked for: 23 actions the screen does not name, and 13 tasks
that take more steps than a person expects, such as 12 to 14 keys to start work on one issue from Flow.

### The prose

The prose is not padded, and it is not plain. It has no filler word, no agentic tic, and no summary that
restates. Every prose reviewer found the opposite fault: a compressed dialect that is the repository's own. It
packs a table of facts into one sentence, uses "as" for six different words (2,572 lines), drops the noun after
a possessive, and almost never says "because" (61 times in the tree). Of 659 sampled passages, 454 pass on one
reading, 69%.

The short texts value the reader's time: refusals, check lines, rules, and tab titles. The long ones make the
reader decode them: the reference pages, the help of the picture verbs (`kit help flow` is 345 lines), the Go
package comments, and the commit subjects, whose median is 131 characters. The repository's five prose rules
stop filler and say nothing about compression, and two of them push writers toward it. The prose page proposes
six rules to add.

## What is done well

Each page ends with what to leave alone. In short:

- One source, the verb's header, feeds help, the form, completion, and the argument check.
- A refusal says what is wrong and names the command that fixes it.
- The table: grouping, filters, presets, frozen headings, and a correct drawing at every size.
- kittui's packages are layered, all 23 are at 100% of statements, and the suite is clean under `-race`.
- The forge contract has versions, and a provider declares what its forge lacks.
- `glyphs.json` and `terminals.json` show how a fact is kept once and generated into bash and Go.
- The sweep in `kit work` knows its stash by hash. The earlier review's lost-work findings in it are fixed.
- The short texts, and the absence of filler everywhere.

## Decisions for the owner

The plan waits on these. Each has a recommendation.

1. Which forges v0.1.0 names. The Azure DevOps provider is tested against its own fake alone, and GitLab was
   never called. Recommendation: name GitHub as supported, and call the other two experimental in the README
   and the welcome page until each has run against a live project.
2. The names. Recommendation: keep "change" as kit's word and show the forge's noun where a forge is named;
   keep the verbs `kit audit` and `kit workspace`, and put the verb in each app's title; rename one of
   `kit workspace` and `kit workspaces`, because a released verb cannot change.
3. The Homebrew line and the tutorials site. Recommendation: lead the README with the download lines, and
   publish the site from CI before the release.
4. Whether a write to the forge asks first. Recommendation: every action that writes asks once, with what it
   will change.
5. The six prose rules. Recommendation: adopt them, and rewrite text only where the plan touches it.
6. The specs and the plans. Recommendation: keep the files, and put a dated status line on each.
7. A cap on commit subjects. Recommendation: 72 characters with a verb first, once pull request #1 merges.

## Limits

[The limits page](2026-11-12-review-limits.md) holds these in full. The ones that bear on the plan:

- The tests were counted and sampled, not read. 35 bats files and 112 Go test files are named in no finding,
  and no reviewer read more than 25 of the 85 goldens. A reader per suite, looking for assertions that cannot
  fail and goldens that hold a wrong screen, is the largest piece of review still owed.
- Nothing ran on Linux, though both workflows run on Ubuntu alone. Run `bin/ci` and the release and trust
  reproductions in an Ubuntu container with bash 4.4 and jq 1.7.1 before part 1 is called done.
- Nothing that needs the network was seen: the tap, the published site, the tag rulesets, the pinned SHAs
  against their tags, and a live run of glab and az.
- The interface was judged in tmux on the tests' fake kit, whose fixtures have drifted from kit. "How it will be
  received" is the reviewers' projection. Two people with kittui for an hour each would replace it with
  evidence.
- The timings were taken on a loaded machine. Rerun them on an idle one before quoting seconds.
- No medium finding had a second reader. Give one to each medium finding that a must-ship item rests on.
